Project Kickstart

AI-driven playbook for project initiation — 10 steps to launch a clean, governed, build-ready code repository

After Step-00, each step is one Claude command, run in a fresh session from the kit. It drafts the step's documents in your target repo and opens a PR/MR. The documents become final only when the Product Owner and/or Architect approves and merges it to main.

Commands overview

Every command runs from the kit folder in a fresh Claude session. Each step is covered in detail on the pages that follow.

Initiation · run in order
STEP 00/proj-init-bootstrapRegister target

Clones the project repository from your Git host into an empty or new local folder and registers that clone as the initiation workspace. The command presents a dry run for review and applies it only after you confirm. From then on, every command runs from the kit but operates on the registered clone, so kit files are never copied into the project.

PRODUCES
The local clone, plus .proj-init/state.json in the kit (gitignored). Every later step and utility reads this file to locate the target before doing any git work. It is specific to one machine; to continue elsewhere, re-run Step-00.
STEP 01/proj-init-repo-setupRepo governance

Establishes the repository's governance baseline: the branching convention, the commit message convention, and the self-review checklist every PR/MR must satisfy. Where the Git host and plan permit, it also enables branch protection on main. Rules needed only during initiation are placed in a fenced INITIATION-ONLY block so they can be removed cleanly at the end.

PRODUCES
CONTRIBUTING.md. Steps 02–09 will not start until this file is on main. Its permanent rules govern every contribution for the life of the project; Step-05 extends it and Step-09 finalizes it.
STEP 02/proj-init-productProduct concept

Conducts a structured interview with the Product Owner, one question at a time, to define the product's vision, problem statement, objectives, target users, features, scope boundaries, and success criteria. No answer is assumed; each section is drafted and revised until it is approved.

PRODUCES
docs/PRODUCT.md. The source of truth for product intent: requirements (03) are derived from it, and the README (07) and backlog (08) draw on it. Later changes to scope or goals go through /proj-init-doc-update.
STEP 03/proj-init-prdRequirements

Translates the approved product concept into a formal requirements document: user stories, functional and non-functional requirements, acceptance criteria, out-of-scope items, dependencies, constraints, and risks. Every requirement is stated so that it can be tested.

PRODUCES
docs/PRD.md. Architecture (04) and technology (05) decisions are made against these requirements, and the backlog's epics and stories (08) are derived from them. Its acceptance criteria give the team a testable definition of each feature.
STEP 04/proj-init-architectureArchitecture

Defines the system architecture: components and their boundaries, data design, data flow, integration points, security posture and data classification, and the non-functional approach. It records the key design decisions and the implementation conventions code must follow. The session loads both Architect and Product Owner context, and both must approve.

PRODUCES
docs/ARCHITECTURE.md. The structural boundary for all implementation. Technology choices (05) and engineering rules (06) are derived from it; design changes after initiation go through /proj-init-doc-update.
STEP 05/proj-init-techstackTech stack

Selects and locks the approved technologies (languages and frameworks, datastores, cloud and infrastructure services, key libraries and tools) with the trade-offs behind each choice and their versions and constraints. It also adds the project's build, test, and lint commands to CONTRIBUTING.md as a tooling layer, leaving the Step-01 governance rules untouched.

PRODUCES
docs/TECH-STACK.md + tooling layer in CONTRIBUTING.md. Only technologies listed here may be used; adding or replacing one requires /proj-init-doc-update. Once merged, isolated sandbox spikes may begin.
STEP 06/proj-init-aitoolguideEngineering rules

Defines the engineering rules every contributor follows, human or AI: coding conventions, scope boundaries, banned patterns, testing and documentation rules, decision-escalation criteria, off-limits files, and workflow conventions. The rules are derived from the approved architecture and tech stack. CLAUDE.md points to the shared rules and adds only Claude Code–specific instructions.

PRODUCES
docs/ENGINEERING-RULES.md + CLAUDE.md. Production implementation may start once this is merged. Claude Code reads CLAUDE.md automatically in every session, so AI-assisted work follows the same rules as the team.
STEP 07/proj-init-readmeProject README

Replaces the repository's boilerplate README with the project's real entry point: overview, key concepts, prerequisites, environment setup, install and run, tests, project structure, and links to the source-of-truth documents. Every command in it is executed and verified before commit, and no placeholder may remain.

PRODUCES
README.md (replaced). The first document a new contributor reads and the basis for onboarding. It must be merged before the repository is shared more widely.
STEP 08/proj-init-backlogInitial backlog

Derives the initial epics and stories from the product and requirements documents and presents them for approval before anything is written. Once approved, it creates the work items in the host tracker one at a time through gh or az boards; if neither CLI is available, it records PENDING IDs and manual creation notes.

PRODUCES
docs/BACKLOG.md + host work items. The starting point for sprint planning, which may begin once it is merged. Its presence on main is also the gate for Step-09.
STEP 09/proj-init-finalizeFinalize governance

Converts CONTRIBUTING.md from its initiation form into its permanent form. It removes the INITIATION-ONLY block, markers included, and inserts a DEVELOPMENT-PHASE-GOVERNANCE stub; the permanent rules and the tooling layer remain verbatim. It halts if the initiation markers are missing.

PRODUCES
CONTRIBUTING.md (final). The permanent contribution policy for the development phase. Merging it completes initiation.
CLEANUP/proj-init-cleanupClean up

Closes out the initiation workspace. It verifies that BACKLOG.md is on main and the INITIATION-ONLY block is gone, then, after your confirmation, unregisters the workspace. The target clone and its remote are not modified.

PRODUCES
Deletes .proj-init/state.json; nothing in the target. Frees the kit to register the next project; the finished project stays reachable by the utilities below with --target.
After initiation · any time
UTILITY/proj-init-doc-statusStatus

Produces a read-only status report: which steps are merged to main, which have open PRs/MRs, and which step comes next. With --target <folder>, it reports on a finished or different project without re-registering it.

PRODUCES
A status report in the session; writes nothing. Every step runs this check before it starts; run it yourself to see where a project stands at any time.
UTILITY/proj-init-doc-update <doc>Update a document

Updates a finalized source-of-truth document on a docs/update/<doc> branch, through the same review gate that originally approved it. It analyzes the impact of the change and flags the downstream documents that may need to follow.

PRODUCES
The updated document and a reconciliation checklist, opened as a PR/MR. Keeps the documentation aligned as the project evolves; work through the checklist afterward with one update per flagged document.
Kit maintenance
KIT/proj-init-auditKit audit

Performs a static completeness audit of the kit itself, scoring dimensions such as control-plane execution, step outputs, resumability, question-driven drafting, and adapter parity. It reads kit files only: it never touches a target, runs a script, or invokes git.

PRODUCES
A scored PASS / GAP / FAIL report; writes nothing. Intended for kit maintainers, to catch gaps and drift between the guides, the step registry, and the adapters before teams use the kit.

Step by step

Run every command from the kit folder, one per fresh session. Steps 01–09 share one runner: resolve the target, fast-forward main, check status and preconditions, wait for your yes, branch, interview you one question at a time, draft, commit, then push and open the PR/MR only after a second yes.

Each step card is tagged with where it runs and who acts:

KitRuns in the kit repo. You start each Claude command here, and the guides and templates load from here. TargetLands in your project clone: the step's branch, commits, and documents. HumanNeeds a person to act: confirm, review, approve, or merge. The step's owner (Product Owner and/or Architect) does this.

One step up close

What happens between you, the Claude session in the kit, the target clone, and your Git host during any step from 01 to 09.

After the PR/MR opens

From here on it's your job. The command's job ended when the PR/MR opened.

  1. Give it fresh eyes. Wait at least a few hours, ideally a full day, before reviewing.
  2. Tick the self-review checklist in the PR/MR description: every required section is covered, no upstream doc changed after you branched, and the change went through a PR/MR, not a direct push.
  3. Merge to main. Merging is what makes it final. Step-04 also needs the Product Owner's sign-off.
  4. Start the next step in a fresh session. It fast-forwards main in the target before it checks that the upstream documents are merged.

Rules that hold at every step

One step, one fresh session.Never run two step commands in the same session. Status is checked first, then only the step you asked for runs.
Run from the kit, write to the target.Commands load guides from the kit and do git work in the registered clone. Kit files are never copied in.
Merge = final.A doc on a branch is a draft; a doc on main is final. There are no draft files and no status flags.
Nothing ships without your yes.Explicit confirmation before branching, before every host write, and before every push.
Never on main.No commits or pushes to main, and no force-pushes to shared branches. Every change goes through a PR/MR.
Upstream first.A step stops if any doc it depends on isn't on main, or if its own output is already final (use /proj-init-doc-update instead).
Same machine, same operator..proj-init/state.json is local to one machine. To continue elsewhere, re-run Step-00.
Never assume an answer.Claude asks one focused question at a time until no template placeholder is left.
